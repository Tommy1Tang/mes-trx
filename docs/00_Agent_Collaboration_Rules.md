# MES 项目Agent协作规则（所有Agent必须严格遵守）

> 最后更新：2026-05-28

## 1. 全局规则
所有Agent在项目中工作时，必须严格遵守本规则，违反规则的产出物将被拒收。

## 2. 文档读取规则（渐进式加载）
### 2.1 首次加载必看
Agent启动后必须先读取以下3个文件，获取全局架构、协作规则和开发口径：
1. `00_Blueprint.md` — 全局架构、API路标、文档索引
2. `00_Agent_Collaboration_Rules.md` — 本文件，协作规则
3. `IVD_MES整体开发口径.md` — IVD MES定位、系统边界、L0-L10分层、工艺口径、合规口径、集成口径、一期范围

禁止直接读取其他文档。

### 2.2 按需读取规则
需要具体领域内容时，根据`00_Blueprint.md`中的文档索引，仅读取对应场景的子文档，禁止加载无关文档占用上下文窗口：

| 工作场景 | 需要读取的文档 |
|----------|----------------|
| 架构设计、技术选型 | 00_Blueprint.md + 04_System_Architecture.md |
| 接口开发、联调 | 00_Blueprint.md + 01_Interface_Specification.md |
| 数据库开发、表结构设计 | 00_Blueprint.md + 03_Database_Design.md + 对应L层的表清单和字段字典CSV |
| 项目管理、排期、上线 | 00_Blueprint.md + 02_Project_Plan.md |
| 业务模块开发 | 00_Blueprint.md + 对应模块Router（10~22）+ 30_Feature_Card_Index.md + 对应功能卡 |
| 前端页面开发 | 00_Blueprint.md + 32_前端页面开发风格规范.md + 对应模块Router + 对应功能卡 + 01_Interface_Specification.md |
| 需求确认、变更评审 | 00_Blueprint.md + 00_Requirement_Index.md + 30_Feature_Card_Index.md + 05_Change_Log.md |
| 任务分工、状态同步 | 00_Blueprint.md + 00_Task_Kanban.md + 00_Progress_Snapshot.md |

### 2.3 Absolute Progressive Loading 功能卡规则
业务模块开发必须采用“Router定位、功能卡落地”的上下文加载方式：
- 模块需求文档`10_*.md`至`22_*.md`只作为Router，负责说明模块边界、核心流程、关联关系和功能卡索引。
- 开发级事实以`30_Feature_Cards/30_FC-*.md`为准，单个任务只加载相关功能卡。
- 定位方式优先使用`rg "REQ-XXX-001" 30_Feature_Cards`或`rg "FC-XXX-001" 30_Feature_Cards`。
- 禁止为了一个开发任务一次性加载全部模块文档、全部字段字典或整个功能卡目录。
- 若功能卡缺少页面字段、交互、接口、验收或异常规则，先补功能卡并同步`30_Feature_Card_Index.md`和对应模块Router，再进入开发。

### 2.4 数据库开发按L层加载规则
涉及数据库开发时，禁止一次加载全部147张表。必须按任务所属的L架构层加载：
- 先加载 `IVD_MES整体开发口径.md` 中对应层的说明
- 再加载相关功能卡声明的候选表
- 最后仅加载候选表在`MES系统基础表逐字段数据字典_按优先级_pgsql.csv`中的字段定义
- 新增表/字段前必须读取`MES数据模型治理规范/`中对应规范，DDL只能输出到`docs/sql_changes/`等待人类执行

### 2.5 命名规范必须遵守
所有文档统一存放于`/docs`目录，文件名严格遵循`[两位数字序号]_[大驼峰文件名].md`格式，禁止使用其他命名格式。
开发级功能卡统一存放于`30_Feature_Cards/`，采用`30_FC-模块-序号_功能标题.md`格式，并在正文保留`card_id`、`module_doc`、`source_section`和`requirements`元数据。

## 3. 批次开发工作流规则（绝对强制）

所有业务模块开发必须遵循"**先评审功能卡，再执行开发**"的批次循环模式，禁止跳过功能卡评审直接开发。

### 3.1 开发批次定义
开发按L层依赖链分为12个批次，详见`00_Task_Kanban.md`。每个批次包含一组架构层相关的模块和功能卡。

### 3.2 批次内工作流
每个批次必须按以下两个阶段顺序执行：

**阶段一：功能卡评审（开发前）**
1. 从`30_Feature_Card_Index.md`中定位当前批次涉及的功能卡
2. 将功能卡状态从`待沟通`更新为`沟通中`
3. 整理功能卡中的待确认点（字段取值、业务规则、边界条件、交互细节）
4. 与业务方/人类确认，获得批注或确认
5. 根据确认结果更新功能卡内容和数据模型（CSV）
6. 将功能卡状态更新为`已沟通`

**阶段二：开发执行（评审通过后）**
1. DBA基于已沟通的功能卡和CSV生成DDL → 输出到`docs/sql_changes/` → 人类执行
2. 后端Agent基于DDL + 功能卡生成Java代码（Entity/Mapper/Service/Controller）
3. 前端Agent基于接口规范生成Vue页面
4. QA Agent编写E2E测试
5. Reviewer Agent验收通过后，将功能卡状态更新为`已完成`
6. 进入下一批次

### 3.3 功能卡状态定义
功能卡必须在`30_Feature_Card_Index.md`中维护状态，状态流转如下：

```
待确定 → 待沟通 → 沟通中 → 已沟通 → 开发中 → 已完成
```

| 状态 | 含义 | 触发条件 |
|------|------|----------|
| `待确定` | 需求尚不明确，需要业务方进一步澄清 | 功能卡创建时需求有歧义或缺失 |
| `待沟通` | 需求基本明确，等待批次排期后与业务方评审确认 | 功能卡内容已填写完整，但未经过业务评审 |
| `沟通中` | 正在与业务方进行功能卡评审 | 当前批次已启动阶段一 |
| `已沟通` | 业务方已确认功能卡内容，可以进入开发 | 业务评审通过，无阻塞问题 |
| `开发中` | 后端/前端正在按功能卡实现 | 当前批次已启动阶段二 |
| `已完成` | 代码已开发、测试已通过、评审已验收 | Reviewer验收通过 |

### 3.4 状态管理责任
- **PM Agent**：负责功能卡状态流转管理，在`30_Feature_Card_Index.md`中维护状态列
- **开发Agent**：开始编码前必须确认功能卡状态为`已沟通`，否则禁止开发
- **Reviewer Agent**：验收通过后通知PM将状态更新为`已完成`

### 3.5 批次准入规则
- 批次N的所有功能卡状态必须为`已沟通`或`已完成`，才允许进入批次N的开发执行阶段
- 若批次内有功能卡为`待确定`，必须先完成需求澄清，否则该批次暂缓开发
- 批次间允许部分并行（如L5和L7无依赖时可并行），但功能卡评审必须先于对应批次的开发

## 4. Agent角色分工规则
### 4.1 架构师Agent(01_architect)
- 负责架构设计、模块划分、API路标定义
- 负责更新`00_Blueprint.md`、`04_System_Architecture.md`、`03_Database_Design.md`
- 负责核心技术决策、代码规范制定
- 负责L0-L10架构分层的维护和演进

### 4.2 产品/需求Agent(00_pm)
- 负责需求拆解、用户故事编写、需求文档维护
- 负责更新`00_Requirement_Index.md`、各业务模块Router和`30_Feature_Cards/`开发级功能卡
- 负责一期MVP范围的把控和需求优先级管理
- 负责功能卡状态流转管理，在`30_Feature_Card_Index.md`中维护状态列
- **负责主动引导人类完成功能卡沟通，严格遵守以下行为规范**

#### 4.2.1 功能卡沟通行为规范（绝对强制）

PM Agent沟通功能卡时，**必须主动引导人类**，不能等人类提供信息。每次沟通必须按14项模板逐项检查，主动询问缺失项、提醒待确认项、指出边界和防错要点。

**沟通原则：**
- PM负责把"现场真实怎么做、哪里不能错、出问题谁处理"翻译成功能卡语言，不要求人类自己组织功能卡格式
- 一次只沟通1-3张功能卡，不批量轰炸
- 用业务语言提问，不用技术术语
- 不确定的地方主动标为"待确认"，不要假装已知
- 功能卡允许有"待确认"，但开发前必须清掉

**8条沟通要点（PM必须逐条检查）：**

1. **要说场景，不要只说功能** — 问清楚不同工序/角色/产品的差异，例如"包装工序和配制工序的派工单字段有什么不同？"
2. **每张卡只聊一个功能包** — 不要一次聊整个模块
3. **必须讲边界** — 主动问"这件事谁负责？谁不负责？"，例如"MES只渲染派工单还是也要负责修改？"
4. **必须讲状态流转** — 主动列出状态链，逐个确认：谁能改、什么时候改、改了能不能回退、还能不能编辑、是否要留痕
5. **必须讲防错和拦截** — 每张卡至少问一句："这个功能里哪些情况必须挡住？"
6. **区分自动带出和人工填写** — 主动问"哪些字段从生产订单/MBR/模板自动带出？哪些由现场人员录入？"
7. **讲清楚证据留在哪里** — 主动确认：是否进入EBR、是否进入DHR、是否需要电子签名、是否需要审计追踪、是否要打印/导出、是否保留版本快照
8. **不确定的地方不要硬定** — 主动标为"待确认"，开发前必须和人类清掉

**15项沟通模板（PM每次沟通功能卡时必须使用）：**

```
我要沟通功能卡：FC-XXX-XXX

1. 现场场景：（不同工序/角色/产品的差异）
2. 使用角色：（谁操作、谁审核、谁查看）
3. 前置条件：（必须满足什么才能开始）
4. 主流程：（正常怎么做，步骤1→2→3）
5. 自动带出字段：（从生产订单/MBR/模板/外部系统带出）
6. 人工填写字段：（现场人员必须录入什么）
7. 状态流转：（状态链 + 每个状态的变更权限、回退规则、编辑权限、留痕要求）
8. 防错/拦截规则：（哪些情况必须挡住，挡住后怎么提示）
9. 异常处理：（流程中断、外部系统失败、数据异常时怎么办）
10. 是否打印/导出：（需要打印什么格式、导出什么内容）
11. 是否进入EBR/DHR：（哪些数据进批记录、进DHR汇总）
12. 是否电子签名/审计：（哪些动作需要签名、哪些操作留审计）
13. 外部系统边界：（和SAP/PLM/WMS/SCADA/QMS的职责划分）
14. 页面口径：（页面类型、参考页面、主要按钮、列表字段、表单字段、权限点、状态展示方式，必须符合`32_前端页面开发风格规范.md`）
15. 待确认问题：（PM主动列出所有不确定点，不假装已知）
```

**PM引导流程：**
1. 拿到功能卡后，先读取功能卡现有内容，识别已填写和缺失的项
2. 按15项模板逐项检查，列出已知信息和缺失信息
3. 用业务语言主动向人类提问，一次问2-3个相关问题，不一次性问完
4. 人类回答后，整理成功能卡格式，更新功能卡内容；涉及表、字段、索引、状态枚举的变更，**只能形成数据模型变更建议**，由DBA Agent按`MES数据模型治理规范/`生成CSV/DDL，PM不得直接修改`00_Data_Dictionary.csv`和`MES系统基础表逐字段数据字典_按优先级_pgsql.csv`
5. 标记所有"待确认"项，汇总给人类做最终确认
6. 确认通过后，将`30_Feature_Card_Index.md`中该功能卡状态更新为"已沟通"（状态以索引中的中文状态列为准）

### 4.3 后端开发Agent(03_backend)
- 负责业务模块后端代码开发、接口实现
- 严格遵守`01_Interface_Specification.md`的接口规范
- 代码生成前必须通过`07_代码生成前检查清单`

### 4.4 前端开发Agent(04_frontend)
- 负责PC端和移动端页面开发、交互实现
- 严格遵守`00_Blueprint.md`的API路标准则调用接口
- 页面开发前必须读取`32_前端页面开发风格规范.md`
- 必须复用RuoYi Vue3 + Element Plus现有列表、表单、弹窗、字典、权限、分页和下载模式
- 禁止脱离功能卡和统一风格规范自行设计独立视觉风格

### 4.5 DBA Agent(02_dba)
- 负责数据库设计、性能优化、SQL脚本编写
- 严格遵守`03_Database_Design.md`的数据库规范
- 新增表/字段前必须通过`06_校验规则清单`
- DDL生成必须以`MES系统基础表逐字段数据字典_按优先级_pgsql.csv`为权威来源

### 4.6 测试/QA Agent(05_qa)
- 负责测试用例编写、测试执行、Bug跟进
- 基于需求文档和接口规范开展测试工作

### 4.7 代码评审Agent(06_reviewer)
- 负责代码评审、质量把控、规则合规检查
- 所有代码合并前必须经过评审Agent的检查
- 合规性检查（FDA 21 CFR Part 11、GMP）是评审重点

## 5. 产出物规范
### 5.1 代码规范
- 严格遵循RuoYi框架的代码规范、命名规范
- 生产模块代码统一存放于`/ruoyi-source/ruoyi-production/`目录下
- 前端生产模块代码统一存放于`/ruoyi-ui-source/src/views/production/`目录下
- 代码按L层组织包结构：`com.ruoyi.production.{层名}.{模块名}`

### 5.2 文档规范
- 所有新增文档必须遵循命名规范，加入`00_Blueprint.md`的文档索引
- 文档内容必须清晰、可落地，禁止模糊不清的描述
- 涉及接口的文档禁止写入具体的JSON参数，仅保留路标准则

### 5.3 SQL脚本规范
- 所有数据库变更脚本必须存放于`/docs/sql_changes/`目录下
- 脚本命名格式：`YYYYMMDD_描述.sql`
- 脚本必须包含回滚语句
- DDL生成必须以`MES系统基础表逐字段数据字典_按优先级_pgsql.csv`为权威来源

### 5.4 变更记录规范
- 所有数据模型变更必须记录在`05_Change_Log.md`
- 变更编号格式：`DM-YYYYMMDD-序号`
- 修改核心CSV前必须备份
