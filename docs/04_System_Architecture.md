# 系统架构与集成方案

> 最后更新：2026-05-12
> 变更说明：新增PLM/ThingsBoard/QMS集成方案、合规性设计、运行时架构

## 1. 技术栈选型
完全继承现有RuoYi框架技术栈，无额外新增技术依赖：
- 后端：Spring Boot 2.7.x + MyBatis Plus + Redis + RocketMQ
- 前端：Vue 2.x + Element UI + uniapp(移动端)
- 数据库：PostgreSQL 16
- 部署：Docker + Kubernetes + 双活集群
- 合规：电子签名符合FDA 21 CFR Part 11，符合GMP要求

---

## 2. 系统边界

MES 管"受控执行、现场防错、批记录证据、质量闭环和系统集成缓冲"，不替代以下系统的边界：

| 系统 | 主责 | MES 对接口径 | MES 不应承担 |
|------|------|------------|-------------|
| SAP ERP | 销售、计划、采购、财务、成本、库存账、主数据源头 | 接收生产订单/物料/BOM/Routing/工厂/库存批次参考数据；回传报工/投料/检验结果 | 不做财务库存总账、MRP、采购结算和成本核算 |
| PLM | 产品设计、研发配方、工艺文件、变更源头 | 接收受控配方/文件/ECN/版本/适用范围；转化为MES可执行MBR | 不替代研发设计、文档生命周期和设计评审 |
| WMS | 仓储作业、库内库存、拣配、上架、移库、盘点 | 接收可投料批次/库位/发料结果；回传生产领用/退料/成品入库请求 | 不重做仓储策略、库内路径优化和全量库存账 |
| ThingsBoard/SCADA/PLC | 高频采集、设备状态、实时报警、边缘联锁 | 保存设备映射/点位模型/关键采集结论/告警事件/过程摘要 | 不在主库保存高频原始时序数据，不用MES替代PLC安全控制 |
| QMS/eQMS | 偏差、CAPA、变更、培训、投诉、放行流程 | 记录现场异常/偏差来源/批记录证据；必要时推送QMS建立正式质量流程 | 不完整替代企业级CAPA、供应商质量和投诉管理 |

## 3. 系统集成方案

### 3.1 SAP集成
| 场景 | 方向 | 频率 | 协议 | 异常处理 |
|------|------|------|------|----------|
| 主数据同步 | SAP→MES | 每日凌晨1点 | RFC | 3次立即重试→延迟重试队列→24小时失败告警，每日对账 |
| 生产订单同步 | SAP→MES | 实时+每日批量 | RFC | 同上 |
| 投料过账 | MES→SAP | 实时 | RFC | 先落MES本地事务，再通过Outbox异步发送 |
| 报工过账 | MES→SAP | 实时 | RFC | 同上 |
| 库存同步 | MES↔SAP | 实时+每小时对账 | RFC | 同上 |
| 财务过账 | MES→SAP | 每日凌晨2点 | RFC | 同上 |

**关键设计原则：**
- SAP主数据进入MES后形成参考表和映射表，不直接用SAP原始ID贯穿所有业务
- 投料、报工、检验回传必须先落MES本地事务，再通过Outbox异步发送
- SAP失败不得直接回滚车间已完成的物理动作
- SAP失败进入对账补偿和死信处理，由业务人员或接口运维闭环

### 3.2 PLM集成
| 场景 | 方向 | 触发时机 | 协议 | 异常处理 |
|------|------|----------|------|----------|
| 受控配方下发 | PLM→MES | 配方发布时 | Webhook | 3次重试→死信队列→人工处理 |
| 文件/ECN下发 | PLM→MES | ECN审批通过时 | Webhook | 同上 |
| 版本/适用范围同步 | PLM→MES | 版本变更时 | Webhook | 同上 |
| MBR生成确认 | MES→PLM | MBR模板创建后 | Webhook | 同上 |

**关键设计原则：**
- PLM是设计源头，MES是执行版本源头
- PLM下发设计配方、文件、ECN和适用范围，MES生成可执行MBR版本
- ECN影响运行中工单时，必须进入Safe Hold和上下文刷新机制

**落地表：** `pro_mbr_version`、`pro_mbr_release_record`、`pro_mbr_change_record`、`pro_ecn_order`、`pro_ecn_affected_object`、`pro_mbr_execution_context`、`pro_mbr_context_refresh_log`

### 3.3 WMS集成
| 场景 | 方向 | 触发时机 | 协议 | 一致性保证 |
|------|------|----------|------|----------|
| 领料出库 | MES→WMS | 派工单确认后 | HTTP | 最终一致性，每日对账 |
| 退料入库 | MES→WMS | 退料申请审核后 | HTTP | 同上 |
| 成品入库 | MES→WMS | 生产完工报工后 | HTTP | 同上 |
| 库存查询 | MES→WMS | 实时调用 | HTTP | 同上 |
| 扫码对接 | WMS→MES | 扫码完成后 | HTTP | 同上 |

**关键设计原则：**
- WMS管仓库动作，MES管生产使用
- 退料、报废、成品入库请求通过接口事件异步传递给WMS/SAP

### 3.4 ThingsBoard/SCADA集成
| 场景 | 方向 | 触发时机 | 协议 | 一致性保证 |
|------|------|----------|------|----------|
| 设备映射同步 | MES→ThingsBoard | 设备主数据变更时 | HTTP | 最终一致性 |
| 采集点位配置 | MES→ThingsBoard | 点位定义变更时 | HTTP | 同上 |
| 关键采集值回传 | ThingsBoard→MES | 采集完成后 | Webhook | 同上 |
| 告警事件回传 | ThingsBoard→MES | 告警触发时 | Webhook | 同上 |
| 设备状态回传 | ThingsBoard→MES | 状态变更时 | Webhook | 同上 |

**关键设计原则：**
- ThingsBoard管高频过程，MES管合规结论
- 原始高频遥测保留在ThingsBoard/时序库
- MES只保存与工单、批次、步骤、放行相关的关键值、摘要、告警和曲线引用
- 毫秒级联锁尽量在PLC/边缘侧完成，MES负责规则配置、放行判定和证据固化

**落地表：** `pro_scada_system`、`pro_scada_device_ref`、`pro_equipment_scada_map`、`pro_scada_point`、`pro_operation_data_collect`、`pro_process_monitor_summary`、`pro_scada_alarm_event`、`pro_equipment_state_event`、`pro_oee_summary`

### 3.5 QMS/eQMS集成
| 场景 | 方向 | 触发时机 | 协议 | 回调机制 |
|------|------|----------|------|----------|
| 异常流程触发 | MES→QMS | 异常工单升级时 | Webhook | 30秒超时，3次重试，ACK确认 |
| 偏差处理流程 | MES→QMS | 质量偏差上报时 | Webhook | 同上 |
| 流程结果回调 | QMS→MES | 流程结束时 | Webhook | 同上 |

**关键设计原则：**
- MES记录现场异常、偏差来源、批记录证据
- 必要时推送QMS建立正式CAPA、供应商质量和投诉管理流程
- MES不完整替代企业级QMS功能

### 3.6 OA集成
| 场景 | 方向 | 触发时机 | 协议 | 回调机制 |
|------|------|----------|------|----------|
| 异常流程触发 | MES→OA | 异常工单升级时 | Webhook | 30秒超时，3次重试，ACK确认 |
| 标签/说明书审核 | MES→OA | 标签模板变更时 | Webhook | 同上 |
| 流程结果回调 | OA→MES | 流程结束时 | Webhook | 同上 |

### 3.7 思宇UDI系统集成
| 场景 | 方向 | 触发时机 | 协议 | 校验规则 |
|------|------|----------|------|----------|
| UDI码生成 | MES→思宇 | 生产订单下达时 | HTTP | 符合国家药监局UDI编码规范 |
| UDI码回传 | 思宇→MES | UDI生成完成后 | Webhook | 唯一性、完整性校验 |
| UDI打印 | MES→思宇 | 包装工序打印时 | HTTP | 同上 |

## 4. 运行时架构

### 4.1 Outbox 异步解耦模式
- 所有MES→外部系统的异步事件通过 `pro_transactional_outbox` 表在本地事务内记录
- 独立的Outbox Relay进程轮询并发布事件到消息队列
- 外部系统失败不影响车间执行，进入对账补偿流程

### 4.2 幂等控制
- 所有关键业务请求（投料、报工、签名等）通过 `pro_idempotency_request` 表做幂等校验
- 防止弱网络环境下重复提交

### 4.3 死信隔离
- 多次重试失败的消息进入 `pro_dead_letter_message` 表
- 避免失败消息阻塞主执行链路
- 由接口运维人员人工处理

### 4.4 MBR执行上下文
- 工单下达时预编译MBR规则快照到 `pro_mbr_execution_context`
- 运行时不再实时联表解析MBR模板
- ECN/返工/Hold恢复时通过 `pro_mbr_context_refresh_log` 记录上下文刷新过程

### 4.5 集成对账补偿
- SAP/WMS等外部系统失败后通过 `pro_integration_reconcile_task` 记录重发、冲销、人工补偿
- 每日自动对账，异常数据由业务人员或接口运维闭环

## 5. 合规性设计

### 5.1 GMP合规
- 电子签名符合FDA 21 CFR Part 11要求
- 所有操作留痕，审计日志保留至少5年
- 数据不可篡改，修改需留痕并说明原因
- 支持导出符合GMP要求的电子批记录PDF

### 5.2 电子记录管理
- 所有用于批放行、偏差调查、追溯召回和监管检查的电子数据按电子记录管理
- 关键业务数据只能通过受控流程新增、修改、作废
- 修改必须保留修改前、修改后、修改人、修改时间、修改原因
- 电子记录的归档、检索、留存和权限控制在系统设计阶段定义

**落地表：** `pro_audit_trail`、`pro_e_signature_record`、`pro_ebr_header`、`pro_ebr_step_record`、`pro_ebr_param_record`

### 5.3 电子签名
- 执行、复核、审核、放行、驳回、偏差关闭区分签名含义
- 签名必须绑定用户、角色、动作、对象、时间、原因和签名结果
- 签名前应重新认证，不能仅依赖已登录会话
- 签名后记录不得被无痕修改

**落地表：** `pro_e_signature_record`、`pro_audit_trail`

### 5.4 审计追踪
- 审计日志由统一组件写入，不依赖每个业务页面手写
- 对关键记录的新增、修改、删除、作废、复核、放行均要留痕
- 审计记录原则上只追加，不允许业务人员修改

**落地表：** `pro_audit_trail`

### 5.5 数据安全
- 敏感数据加密存储，传输采用HTTPS
- RBAC权限控制，数据按角色隔离
- 操作审计日志完整，支持追溯
- 备份策略：每日全量备份+增量备份，异地容灾
